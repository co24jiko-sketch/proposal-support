## 基本方針（発注者・受注者レビューで合意した前提）

### AI の位置づけ

| 原則 | 内容 |
|---|---|
| **AI 出力は下書き** | 提出版そのものではない。担当技術者が内容・専門性・契約義務の妥当性を確認する |
| **人間の責任** | 記載内容は契約義務になり得る。最終提出の責任は受注者側の担当者・承認者にある |
| **提案は1つ** | 複数案を生成して最高点だけ選ぶ運用はしない。UI・プロンプトとも **1軸・1案** に固定 |

### 専門性のリスク

AI が一般論で地質リスク等を書くと、現地と合わない・図書の範囲を超える・技術者が責任を取れない、といった問題がある。

- **既知情報・計画骨子が空** のときは文案生成を **止める** か、**「要技術者確認」** フラグ付きで出す（実装時に決定）
- 着目点の具体性は **専門家の判断** が主。AI は材料を組み立てる補助

## 完成時のアウトプット像

| 現状（Phase 1〜4） | 完成像（Phase 5 以降） |
|---|---|
| 新規案件の入力がそのまま Word / PDF に入る | **様式－１０** の4欄に、AI が考えた **原稿案（下書き）** が収まる |
| 固定の簡易テンプレート | 会社指定の `.docx` 様式への流し込み |
| LLM 未接続 | 評価テーマ・提案の軸等を材料に文案を生成 |

### 様式の4欄（発注者要件）

| 欄 | 発注者が求めること（要約） |
|---|---|
| **１）提案の概要** | 簡潔に。提案は **1つだけ**（複数提出しても最高点1つのみ評価）。記載内容は契約義務になり得る |
| **① 着目点** | 留意事項・地域特性・背景。**業務内容と提案内容の関係**が評価者に伝わること |
| **② 詳細な内容** | 着目点に基づく具体的方法・手順。「必要に応じて」「～に努める」「できる限り」等の **あいまい表現は評価されない** |
| **③ 効果** | エビデンス・根拠・実績。可能なら **定量的**。新手法は従来工法との比較 |

### 作成例から見える文章の型

- **概要**: 1行のキャッチ（提案の軸）＋ 2〜3文の背景・課題・狙い。「～と考える」で締める
- **着目点**: 番号付き（１）（２）…。見出し＋根拠の説明
- **詳細**: **手順（１）（２）…**。体制・方法・機材を具体的に
- **効果**: **効果（１）（２）…**。任意で過去業務名・テクリス番号を引用

## 提出までのフロー（Phase 5 以降の想定）

```
新規案件（基本情報・評価テーマ・仮の軸）
  → 入札図書確認・採点基準適用
  → 提案の軸を確定
  → 生成前チェック（材料の揃い確認）
  → AI 文案生成（下書き・1案）
  → 担当技術者が内容を確認・修正
  → 適合チェック
  → 承認申請 → 部長・支社長承認
  → 提出版 PDF
```

※ 人手編集後の Word 再取込は将来対応（現行 Phase 2 では未実装）。

## AI に渡す材料一覧

### 必須（新規案件 Step 1）

| 材料 | AI が主に使うこと |
|---|---|
| **評価テーマ** | 全体の論調。着目点・手順・効果の方向づけ（例: 品質確保） |
| **基本情報** — 業務件名 | 業務種別・文体のレベル |
| **基本情報** — 発注者 | 国交省・自治体・民間等。トーン・参照規準の違い |
| **基本情報** — 場所 | 地域・路線・地形地質の文脈 |
| **基本情報** — 目的（調査目的・範囲） | スコープ。「何を明らかにするか」 |

### 文案生成前の必須（いずれか）

| 材料 | 入力タイミング | AI が主に使うこと |
|---|---|---|
| **入札図書 PDF** | チェックリストタブ | 評価観点・**発注者が明示した**留意事項・業務範囲・記載ルールの遵守 |
| **発注者明示の留意事項テキスト** | チェックリストタブ（PDF の代替） | 上記と同様。PDF が無い場合の必須代替 |

> **レビュー反映（2026-07-02）**  
> 入札図書は「推奨」から **文案生成前の必須** に格上げ。  
> PDF と留意事項テキストは **どちらか一方以上** 必要（併用可）。

### 強く推奨

| 材料 | 入力タイミング | AI が主に使うこと |
|---|---|---|
| **提案の軸（仮 → 確定）** | 仮: Step 1／**確定: 入札図書確認後・文案生成前** | 概要1行・着目点・手順・効果の一貫したストーリー |
| **既知の地質情報** | 新規案件 Step 1 | 着目点・手順の具体化 |
| **調査計画の骨子** | 新規案件 Step 1 | 手順欄の骨組み |
| **採点基準マスタ** | チェックリストタブ | 評価者の観点との整合。触れるべき論点の漏れ防止 |

### 任意

| 材料 | 入力タイミング | AI が主に使うこと |
|---|---|---|
| **過去実績**（類似案件名・テクリス番号・要点） | 文案生成前（効果欄用） | 効果③の根拠・実績引用。**事実のみ**（案件ごとに有無が異なる） |
| **関連業務メモ** | 新規案件または文案前 | 関連業務との連携・整合（作成例①タイプ） |
| **工期目安** | 新規案件 Step 1 | 概要・手順の補足 |

## 各材料の役割（詳細）

### 評価テーマ（必須）

作成例では `〔評価テーマ〕品質確保` のように、提案全体の論調を決める。

同じ「地質調査」でも、テーマが「工期短縮」なら着目点・手順・効果は別物になる。**プロンプトの最上位パラメータ**として必須。

### 発注者（必須）

国交省系・自治体・民間等で、提案のトーンや参照する規準が変わる。件名・場所・目的と並べて必須材料とする。

### 基本情報（件名・場所・目的）

**読み取れること（比較的安定）**

- 件名 → 業務種別（地質調査 / 地すべり / トンネル等）
- 場所 → 地域名・一般的な地形地質のイメージ
- 目的 → 調査・評価のスコープ

**単独では不足すること**

- その案件固有のリスクの取捨選択
- 提案ストーリー（→ **提案の軸** が担う）
- 手順の具体性（→ **既知情報・計画骨子** が担う）
- 発注者が明示した評価ルール（→ **入札図書** が担う）

### 提案の軸（仮 → 確定）

**設計判断**

| 段階 | タイミング | 意味 |
|---|---|---|
| **仮** | 新規案件 Step 1（タイミング A） | 入札検討の初期方針。「何で勝つか」のたたき台 |
| **確定** | 入札図書確認後・文案生成前 | 図書の留意事項・評価観点を踏まえた最終方針 |

作成例の概要1行が確定後の軸に相当する。

| 作成例 | 提案の軸 |
|---|---|
| 作成例① | 関連業務との密な連携と、複数専門技術者による確認体制 |
| 過去提案書例② | 地質リスクの網羅的抽出と、後続業務への円滑な引継ぎ |

| 欄 | 軸の効き方 |
|---|---|
| １）概要 | 軸を冒頭に展開 |
| ①着目点 | 軸を実現する着眼点に分解 |
| ②詳細 | 軸を達成する手順として具体化 |
| ③効果 | 軸がもたらす効果として帰結 |

**未入力時（将来 UI）**: 入札図書＋評価テーマから軸の候補を2〜3案提示し、ユーザーが1つ選択してから全文生成。

### 既知情報・計画骨子（強く推奨）

着目点・手順の **具体性** の主な材料。入札図書にそのまま書いてある内容ではなく、**担当者・専門家の知見**を反映する欄。

### 入札図書 PDF / 留意事項テキスト（文案生成前必須）

#### 入札図書が担うこと

| 担う | 担わない |
|---|---|
| 評価の観点・配点・記載要領 | 着目点の文言そのものの自動生成 |
| 発注者が **明示した** 留意事項 | 図書に無いリスクの専門家判断部分 |
| 業務範囲・成果品の境界 | 提案ストーリー全体の構成 |
| 提案1つ・契約義務等の **ルール** | |

> **訂正メモ（2026-07-02）**  
> 着目点の具体的内容（破砕帯・湧水・空洞など）は、入札図書の写しではなく、  
> **提案の軸 ＋ 既知情報・計画骨子 ＋ 専門判断** で構成される。  
> 入札図書は「着目点を拾うため」ではなく、「評価ルールと明示要件を外さないため」に渡す。

**発注者視点**: 留意事項に触れているかが評価の最初のチェックになる。図書または留意事項テキストは実務上必須。

### 採点基準マスタ（強く推奨）

`lib/proposal/scoring-templates.ts` の仮マスタ（正式基準整備後に差し替え）。

受注者側の漏れ防止に加え、**発注者が採点表で設計した観点**との整合に使う。「任意」から格上げ。

### 過去実績（任意）

| 状況 | 効果欄の書き方 |
|---|---|
| 実績あり | 業務名・年度・テクリス番号を引用（作成例①） |
| 実績なし | 定性的効果＋手法の妥当性（過去提案書例②） |

案件ごとに有無が決まるため必須にしない。**入力する場合は事実のみ**。虚偽・誇張は評価で信頼を損なう。

## AI 生成時の禁止・推奨ルール（プロンプト設計用）

### 避ける表現（発注者要領）

- 「必要に応じて」
- 「～に努める」
- 「できる限り」
- 履行があいまいになる記述全般

### 推奨する文体

- 「～する」「～を実施する」「～を構築する」など断定的・具体的な表現
- 手順は番号付き（手順（１）（２）…）
- 着目点・効果も番号付き

### 将来検討: 留意事項との対応

発注者明示の留意事項ごとに、着目点・手順のどこで触れたかを一覧表示する（適合チェックの拡張）。

## 現行ツールとのギャップ

| 項目 | 現状 | Phase 5 以降 |
|---|---|---|
| 新規案件フォーム | 件名・発注者・場所・目的・既知情報・骨子 | **評価テーマ**・**提案の軸（仮）** を追加（予定） |
| 提案の軸 | なし | 入札図書確認後に **確定** する UI（予定） |
| 文案生成 | 入力を `document-content.ts` にそのまま流す | AI が4欄の **下書き** を生成 → 様式－１０に流し込み |
| 入札図書 | チェックリストタブで PDF アップロード（任意） | 文案生成前の **必須** 材料 |
| 生成前チェック | なし | 材料の揃い確認（予定） |
| LLM | UI に停止スイッチのみ（未接続） | API 接続・プロンプト実装 |
